# InkLayer Roadmap

> Status: active project roadmap
> Last updated: 2026-08-12
> Current baseline: Core implementation commit `1b68cde` is on `origin/main`

This document is the versioned source of truth for work after the first complete
InkLayer Core baseline. Completed implementation history remains in
`docs/implementation-progress.md`; architectural ownership remains normative in
`docs/core-boundary.md`. Personal notes belong in ignored `TODO.local.md`, not in
this roadmap.

## Status rules

- `[ ]` means not started.
- `[-]` means actively in progress and must name the active branch or pull request.
- `[x]` means complete with reproducible evidence linked or named below the task.
- A task is not complete because an API or file exists; its stated acceptance
  criteria and relevant tests must pass.
- Product-semantic changes, canonical-data compatibility changes, publishing,
  and removal of framework fallback code require explicit review.

Task prefixes identify ownership: `CORE` belongs to this package, `REACT` and
`VUE` belong to their framework adapters, and `RELEASE` spans all consumers.

## Current direction

The next milestone is a Core release candidate suitable for framework adoption.
React integrates first because it provides the existing gesture and Viewer
reference behavior; Vue then consumes the same stable contracts. Duplicate
framework engines are removed only after parity tests pass.

## Milestone 1 — Core release candidate

### P0: documentation and public contract

- [x] **CORE-001 — Zero-configuration PDF.js worker**
  - Core ships a version-matched worker and resolves it for ESM and CommonJS.
  - `workerSrc` remains an optional self-hosting/CSP override.
  - Evidence: package check, packed Vite consumer, Vanilla Chromium E2E.
- [x] **CORE-002 — Range loading and structured load progress**
  - Progress distinguishes `probing`, `downloading`, and `parsing`.
  - Range accounting counts unique validated byte intervals.
  - Evidence: Viewer/Range tests and Vanilla progress presentation.
- [ ] **CORE-003 — Public API review and release-candidate freeze**
  - Review every root and secondary export for naming, optionality, lifecycle,
    error semantics, and framework-neutrality.
  - Document deprecated compatibility events separately from preferred APIs.
  - Done when API docs, declarations, package exports, and consumer examples
    agree and any intended breaking changes are recorded before adapter work.
- [ ] **CORE-004 — Documentation consistency gate**
  - Add automated checks for stale version/test-count claims and mandatory Worker
    configuration examples.
  - Done when maintained documentation contains no known contradiction with the
    current package and the check runs under `npm run check`.

### P0: real network and consumer evidence

- [ ] **CORE-010 — Real HTTP Range integration server**
  - Test actual `HEAD`, `206`, `Content-Range`, overlapping chunks, cancellation,
    unsupported fallback, network failure, credentials, and custom headers.
  - Verify progress events against bytes served by the test server rather than
    only mocked `fetch` responses.
  - Done when the integration suite runs locally and in CI without an external
    network dependency.
- [ ] **CORE-011 — URL-loading Vanilla scenario**
  - Add a locally served PDF large enough to show Range requests and meaningful
    loading progress.
  - Preserve the generated byte-source and encrypted-password scenarios.
  - Done when Chromium E2E observes Range mode, progress, ready state, reload,
    cancellation, and a console without errors.
- [ ] **CORE-012 — Consumer build matrix**
  - Keep the packed Vite consumer and add at least one Webpack-based/Next.js SSR
    consumer check for root import, Viewer import, worker asset resolution, CSS,
    and production build.
  - Done when the supported build-tool matrix is explicit and reproducible.
- [ ] **CORE-013 — Browser support declaration**
  - Run Viewer, selection, annotation interaction, print preparation, Worker,
    Range, and pinch tests in Chromium, Firefox, and WebKit where supported.
  - Record intentional exclusions instead of implying universal compatibility.

### P1: interaction, accessibility, and resilience

- [ ] **CORE-020 — Keyboard and accessibility contract**
  - Define keyboard selection movement/deletion, focus ownership, FreeText focus,
    TextLayer menu handoff, reduced motion, and screen-reader responsibilities.
  - Core owns direct-document behavior; adapters own labelled product controls.
- [ ] **CORE-021 — Rotation and mixed-page fixtures**
  - Add real PDFs containing rotated pages, different page boxes, mixed sizes,
    native annotations, and cross-page selections.
  - Verify Canvas, TextLayer, annotation coordinates, thumbnails, watermark,
    print, and export against the same fixtures.
- [ ] **CORE-022 — Long-document lifecycle stress**
  - Exercise virtual scrolling, search, thumbnail churn, zoom, cancellation, and
    document replacement on a large deterministic fixture.
  - Record stable performance evidence without enforcing machine-specific times.
- [ ] **CORE-023 — Error recovery examples**
  - Demonstrate retry for URL failures, Range failures, incorrect passwords,
    rendering failures, and cancelled work using structured Core errors.

## Milestone 2 — React adapter migration

- [ ] **REACT-001 — Baseline and mapping inventory**
  - Map every existing React Viewer/store/painter/editor/gesture/export path to a
    Core API, adapter UI responsibility, or explicitly retained product policy.
  - Capture the current React test baseline before modifications.
- [ ] **REACT-002 — Thin Viewer adapter**
  - Replace React PDF loading, Worker setup, password lifecycle, Range/loading
    state, navigation, layout, zoom, and pinch implementation with Core calls and
    subscriptions.
  - React retains components, route state, translations, and product layout.
- [ ] **REACT-003 — Thin annotation adapter**
  - Replace framework annotation stores, Painter/editors, selection geometry,
    transforms, FreeText lifecycle, and text markup construction with Core.
  - Do not expose Konva nodes or introduce a React-specific persisted model.
- [ ] **REACT-004 — Sidebar and command integration**
  - Connect React thumbnails, outline, search, comments, watermark controls,
    print, import, PDF export, and Excel export to Core results and commands.
- [ ] **REACT-005 — React parity gate**
  - Prove legacy-data loading, all tools, keyboard/pointer/touch behavior,
    selection-first markup, multi-page layout, password, print, export, teardown,
    and product UI behavior.
  - Done when the agreed React suite and new adapter E2E pass with no fallback
    engine used on tested paths.

## Milestone 3 — Vue adapter migration

- [ ] **VUE-001 — Baseline and mapping inventory**
  - Repeat the behavior mapping against Vue-specific fixes and capture its clean
    pre-migration test baseline.
- [ ] **VUE-002 — Viewer and annotation adapters**
  - Integrate the same Core contracts used by React; Vue retains components,
    composables for lifecycle wiring, translations, and product presentation.
- [ ] **VUE-003 — Vue parity gate**
  - Run the same shared behavior matrix as React plus Vue-specific regressions.
  - Any required engine behavior change must be implemented and tested in Core,
    not patched only inside Vue.
- [ ] **VUE-004 — Cross-framework consistency suite**
  - Use shared fixtures and commands to compare canonical annotations, Viewer
    state, import/export results, and errors across React, Vue, and Vanilla.

## Milestone 4 — Legacy removal and release

- [ ] **RELEASE-001 — Remove duplicated framework engines**
  - Delete old Viewer, Painter, editor, store, geometry, Worker, and gesture code
    only after both framework parity gates pass.
  - Preserve intentional compatibility adapters and documented migrations.
- [ ] **RELEASE-002 — Versioning and changelog**
  - Establish semantic-version policy, changelog format, migration guide, package
    provenance, and release notes derived from reproducible checks.
- [ ] **RELEASE-003 — Publish dry run**
  - Install the exact tarball in React, Vue, Vanilla, Node SSR, and the declared
    consumer matrix; verify asset paths and package contents.
- [ ] **RELEASE-004 — First reviewed package release**
  - Requires explicit approval after CI, browser matrix, adapter parity, migration
    documentation, and publish dry run are green.

## Deferred decisions

These items remain outside the current milestone until product requirements are
specified:

- backend-enforced or tamper-resistant watermarking;
- trusted decrypt/re-encrypt service for vector-preserving protected-PDF output;
- server persistence, realtime transport, conflict resolution, and audit policy;
- OCR, document editing, form authoring, signature trust, and PDF redaction;
- mobile-native adapters beyond browser touch interaction.

## Immediate execution order

1. Complete `CORE-003` and `CORE-004`.
2. Implement `CORE-010` and `CORE-011` together.
3. Establish `CORE-012` and `CORE-013` before declaring the release candidate.
4. Start `REACT-001`; do not remove existing React engine code yet.
5. Begin Vue migration only after the React integration identifies any missing
   Core contract and those changes are stabilized.
